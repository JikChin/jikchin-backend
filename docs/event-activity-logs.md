# 경기 활동 로그와 월별 보관

## 어떤 기능인가요?

활동 로그는 경기에서 일어난 일을 적는 일기입니다. 월별 파티션은 그 일기를 월마다 다른 서랍에 넣는 방식입니다. 오래된 일기를 한 장씩 지우지 않고, 보관 기간이 끝난 서랍을 통째로 비웁니다.

모집글 생성(+5), 신청 수락(+2), 직접 참가 등록(+2), 리뷰 작성(+3)을 기록합니다. 직접 참가 등록은 시스템 경로이므로 actor_id는 비워 두고 subject_id에 참가자를 기록합니다. 업무 저장과 로그 저장은 같은 트랜잭션입니다. 로그 저장이 실패하면 업무 저장도 취소되고, 업무가 취소되면 로그도 남지 않습니다. 과거 업무 데이터는 자동으로 소급 적재하지 않습니다.

이 점수는 활동 발생 이력입니다. 탈퇴·리뷰 삭제 등을 반영한 현재 상태 점수나 Redis 랭킹이 아닙니다. 기존 리뷰 통계는 그대로 사용합니다. 아웃박스와 Redis 연동은 이번 구현에 포함하지 않습니다.

## 보관 기준

UTC 기준으로 **지난 12개월 전체와 이번 달**을 보관합니다. 정확히 365일 보관하는 정책은 아니며, 가장 오래된 기록은 약 13개월까지 남습니다.

- UTC 2026-09-16: 2025-09부터 보관, 2025-08까지 삭제 대상.
- UTC 2026-10-01: 2025-09 파티션 전체가 삭제 대상.
- 이번 달 이후 3개월까지 미리 생성합니다.

매일 한국 시간 새벽 3시에 관리 작업을 실행합니다. 저장·월 경계는 UTC라서 한국 시간 매월 1일 새벽 3시에는 아직 UTC 전월입니다. 이 일정에서 새 월의 삭제는 한국 시간 2일 새벽에 반영됩니다. 한국 달력과 정확히 맞춰야 한다면 저장 시각과 월 경계 정책을 함께 바꿔야 합니다.

## 설치 및 활성화

1. 적용할 서비스 DB를 선택하고 `docs/sql/event-activity/V001__create_event_activity_logs.sql`을 실행합니다. 이 SQL은 자동 실행되지 않습니다. 이미 존재하는 테이블에 재실행하지 않습니다. JPA 엔티티로 관리하지 않으므로 Hibernate가 생성하거나 변경하지 않습니다.
2. 기록과 삭제는 끈 상태에서 관리 작업만 일시적으로 활성화합니다. 아래 환경 변수를 애플리케이션 실행 환경에 설정하고 재시작합니다.

```properties
ACTIVITY_LOG_ENABLED=false
ACTIVITY_LOG_PARTITION_CRON=0 * * * * *
ACTIVITY_LOG_DELETE_ENABLED=false
```

최초에는 `p_before`와 `pmax`만 있습니다. 관리 작업이 실행되면 월별 서랍이 만들어집니다. 다음 쿼리로 이번 달과 이후 3개월까지 생성됐는지 확인합니다.

```sql
SELECT PARTITION_NAME, PARTITION_DESCRIPTION
FROM information_schema.PARTITIONS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME = 'event_activity_logs'
ORDER BY PARTITION_ORDINAL_POSITION;
```

3. 월별 생성 성공을 확인하면 아래처럼 바꾸고 재시작합니다.

```properties
ACTIVITY_LOG_ENABLED=true
ACTIVITY_LOG_PARTITION_CRON=0 0 3 * * *
ACTIVITY_LOG_DELETE_ENABLED=false
```

4. 삭제 후보 로그와 보관 정책을 확인한 후 자동 삭제를 활성화하고 재시작합니다.

```properties
ACTIVITY_LOG_DELETE_ENABLED=true
```

삭제는 되돌릴 수 없습니다. 장기 보관이 필요하면 먼저 별도 백업/아카이브를 마련해야 합니다. 이번 구현은 아카이브를 수행하지 않습니다. 설정을 생략하면 기록·스케줄·삭제 모두 비활성화됩니다. 기록을 활성화하기 전에 테이블이 있어야 합니다.

## 안전하게 서랍을 관리하는 방법

서버가 여러 대여도 같은 DB의 GET_LOCK을 얻은 하나만 작업합니다. 잠금 획득부터 DDL과 해제까지 같은 DB 연결을 사용합니다. 미래 파티션을 먼저 생성하고, 성공한 뒤 오래된 파티션을 삭제합니다. 실패하면 다음 실행에서 실제 DB 상태를 다시 읽습니다.

파티션 이름뿐 아니라 실제 월 경계, 분할 방식, 분할 컬럼도 검증합니다. 예상과 다른 구조라면 삭제하지 않고 오류를 남깁니다. 메타데이터 잠금 대기는 5초로 제한하며, 이 값은 전체 DDL 실행 시간 제한이 아닙니다. 작업 후 연결의 원래 설정을 복구합니다.

`pmax`는 미래 데이터의 임시 서랍입니다. 미리 만드는 작업이 실패해 데이터가 쌓이면 이후 분할 비용이 커질 수 있으므로 관리 실패 로그를 모니터링합니다. `p_before`는 초기 보관 범위보다 오래된 데이터의 예외 서랍이며 자동 삭제하지 않고 데이터가 있으면 경고합니다. 파티션 삭제 후 첫 월 파티션의 하한이 넓어질 수 있으므로 이 테이블로 과거 시각을 임의 적재하지 않습니다. 현재 기록기는 서버의 현재 UTC 시각만 사용합니다.

로그에는 FK를 두지 않습니다. 원본이 없어져도 사건의 ID는 남습니다. `UNIQUE(idempotency_key, occurred_at)`은 동일 키·동일 시각 중복만 막으며 키 전체의 유일성을 보장하지 않습니다. 현재는 업무 상태와 원본의 중복 방지 규칙을 함께 사용합니다. 향후 비동기 재처리를 붙이면 발생 시각을 재사용하고 별도 중복 처리 정책을 설계해야 합니다.

## 관리자 조회

기존 ADMIN 권한이 필요합니다. 기록 기능을 켰을 때만 API가 열립니다. 날짜 입력은 UTC 시각이며 시작은 포함, 끝은 제외합니다. 반환 점수는 기간 내 활동의 합계입니다.

```http
GET /api/admin/event-activities?from=2026-09-01T00:00:00&to=2026-10-01T00:00:00&size=50
GET /api/admin/event-activities?from=2026-09-01T00:00:00&to=2026-10-01T00:00:00&eventId=101&type=REVIEW_CREATED
GET /api/admin/event-activities/monthly?month=2026-09&limit=20
```

목록은 최신순입니다. 다음 페이지는 응답의 nextCursor에 있는 occurredAt과 id를 cursorAt, cursorId로 함께 전달합니다. size와 limit은 1~100입니다. 현재 보관 범위를 벗어난 요청은 거절합니다. 월별 조회는 원본을 집계하며 별도 통계 테이블은 만들지 않습니다.

## 검증과 성능 해석

```bash
./gradlew test
```

업무/로그의 함께 저장·롤백, 기록 실패 시 업무 롤백, 기간 집계와 커서 조회, 삭제 월 경계, 잘못된 파티션 구조 거절을 테스트합니다. H2는 업무 흐름을 검사하며 MySQL 파티셔닝을 대신 검증하지 않습니다.

별도 일회용 MySQL 8.0 서버에서 실제 SQL 생성, 월별 분할, 만료 삭제, 반복 실행, 다른 연결의 잠금 보유 시 작업 건너뛰기를 검증할 수 있습니다. 아래 테스트는 비밀번호 없는 로컬 테스트 root 계정을 사용하고 무작위 이름의 전용 DB를 생성·제거합니다. 운영 서버에 연결하지 않습니다.

```bash
ACTIVITY_MYSQL_TEST_URL='jdbc:mysql://127.0.0.1:23307/mysql?allowPublicKeyRetrieval=true&useSSL=false' \
./gradlew test --tests '*ActivityPartitionMysqlTest'
```

기존 수동 실험에서 1천만 건의 12월 집계는 일반 인덱스 테이블 평균 300ms, 파티션 테이블 평균 308.4ms였습니다(각 5회). 파티셔닝의 조회 개선을 입증한 결과가 아닙니다. 849,315행 삭제는 DELETE 50.04초, DROP PARTITION 0.15초였으나 단일 측정입니다. 이 기능의 도입 근거는 월별 보관·삭제 관리이며, 운영 환경에서도 동일한 배수의 성능을 보장하지 않습니다. 월별 통계 조회 자체가 병목이면 별도 집계 테이블을 검토합니다.
